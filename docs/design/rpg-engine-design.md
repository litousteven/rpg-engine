## 0. 设计原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | 代码规则主导 | 判定权、数值权、状态变更权全部在确定性引擎。LLM 是外设，不是内核 |
| P2 | 意图是状态的唯一入口 | 状态变化只能来自通过校验的结构化意图（intent）。正文是渲染结果，永不回流状态 |
| P3 | 行动空间封闭 | 玩家与 NPC 只能从引擎生成的行动菜单行动。菜单即边界，菜单外不存在动作 |
| P4 | 即兴是组合，不是发明 | 允许在原语集合与预算内组合新实体（自定义毒药）；不允许发明新机制 |
| P5 | LLM 可拔 | 拔掉所有 LLM，游戏用状态机 NPC + 模板文案继续完整可玩。LLM 提升质感，不提供可行性 |
| P6 | NPC 分级 | L0 状态机是主体，L2 LLM 是关键少数；L1 舞台指令让两者都为剧情服务 |
| P7 | 确定性可重放 | 种子 RNG + 事件日志：同输入同输出，bug 可复现、平衡可统计 |
| P8 | Agent 不互通 | LLM 之间不直接对话；一切通信经引擎中转、结构化、带 revision 门控 |

P2 与 P3 合起来消灭 dsh-tavern 中成本最高的一类问题（从自然语言反推状态、结算审计、防作弊、重试回执）。dsh-tavern 的 MVU「提议-校验-审计-重试」管线（见 `tavern-plugin/lib/domain/mvu-background-settlement.js`）在本设计中从核心降级为一个外设接口协议：协议与校验复用，「从正文推断状态」的方向删除。

P5 是 P1 的验收标准：LLM 宕机时，L2 NPC 自动落回 L0 状态机、增富菜单消失只剩基础菜单、文案降级为模板——游戏继续运行，只是变糙。故事弧分激活模式（§10）：`director` 模式弧依赖 Director，拔掉 LLM 时不实例化、不推进；`auto` 模式弧按入口条件确定性推进；确定性任务与事件照常。

## 2. Agent 拓扑与权限矩阵

拆分原则（承自 dsh-tavern 的教训）：不按任务类型拆，按**上下文形状**（各自要看什么）、**写权限**（各自能产出什么）、**调用频率/延迟等级**三件事拆。每多一个常驻 Agent 就多一份稳定前缀和 token 成本，能合并就合并——前台体验 Agent 用「一个会话 + 两种任务模式」承载正文渲染与菜单增富，对应 dsh-tavern 后台子 Agent 的任务模式复用（`tavern-plugin/lib/background-agent-task.js`）。

| 角色 | 频率 | 读权限 | 写权限（产出物） |
|---|---|---|---|
| 玩家（UI） | 每回合 | 公开状态、行动菜单 | 菜单选择；命名/风味文本（仅数据） |
| 前台体验 Agent | 每回合 | 事件流、结算结果、POV、检索工具 | 正文（仅入归档）；菜单候选（校验后混入） |
| Actor Agent | 每回合 × 关键 NPC | **受限 POV**（战争迷雾 = 上下文隔离）+ 自己的菜单 | intent（一次性提交） |
| Director Agent | 每 N 回合 | 全局摘要、任务状态、节奏指标 | 舞台指令（闭集词汇）；任务阶段提议（图内）；弧操作提议（池内 select/advance/abort）；均走校验 |
| ContentGen | 离线/按需 | 世界书、素材请求 | 资产草案（schema 校验后入库） |

关键点：

1. **玩家侧没有解释器 Agent**。玩家不输入自由文本，行动全部来自菜单。这消灭了 NL→intent 翻译这个最难、最不可靠的环节。
2. **POV 受限是特性不是限制**。Actor 只看到自己视野内的状态（战争迷雾、情报隔离），既防全知作弊，也让 LLM 上下文天然变小。
3. **Agent 间不直接对话**（P8）。Director 对 NPC 的安排走舞台指令总线（第 3 节）；前台体验与 Director 之间经引擎中转结构化消息，并带 revision 门控（见第 12.2 节）。

## 3. NPC AI 三层

普通 NPC 由简单规则操控，同时接受 Director 与叙事层的安排。分三层实现：

### L0：效用 AI + 行为树（主体，纯代码）

每个 NPC 定义一组驱力（生存、恐惧、忠诚、贪婪、领地、好奇……）与效用函数，对候选动作打分后确定性选择（可注入种子扰动）。多步例程由行为树执行。毫秒级、可批量：一场百人混战没有任何压力。

L0 NPC **没有台词决策权，但有台词渲染权**：效用 AI 决定「求饶」这个 intent，具体说什么由前台体验 Agent 代笔（渲染层）。**台词渲染的降级路径**：LLM 不可用时，按 intent verb + NPC 画像（语气、身份）从模板文案库（§14-7，按 intent 索引的内容资产）选择模板并填充参数——离线时 NPC 结构性「能行动也能说话」，不会哑巴。这样普通 NPC 便宜但叙事上不僵死。商人的 purse 与画像（§8.2）同为 NPC 数据字段，直接进效用函数与定价修正。忠诚驱力指向 NPC 当前 membership（§9）——倒戈后自动重定向。

### L1：舞台指令总线与提议通道（Director 的指挥通道）

Director 对引擎的输出全部是**结构化提议**，分两类，都走同一校验管线并带回执：

**舞台指令**（对 NPC 的安排）：闭集词汇，每条映射为 L0 效用函数的覆盖或硬目标：

```text
指令 = { verb: guard_position | retreat | feign | act_afraid | volunteer_info
              | withhold_info | escalate | de_escalate | converge | scatter
              | protect | ignore | ...,
         target: NPC ID 或角色查询（如「距玩家最近的 3 名卫兵」）,
         ttl: 回合数或解除条件,
         strength: 硬目标覆盖 | 效用偏置 }
```

三条硬规则：

1. **指令本身也是 intent**，走同一校验管线——导演不能让瘸腿 NPC 冲锋，物理与能力校验会拒绝（带回执，Director 可换指令）。
2. **指令记账**：何时、为何（Director 附带一句理由摘要）、影响谁，全部进舞台指令账本，可审计、可在回放中检视。
3. **对 L2 同样生效**：Actor Agent 在自己的 POV 中看到指令作为强建议，但仍在行动菜单内决策。

**弧操作**（对故事层的安排，G18）：提议通道从「图内任务阶段」扩展到弧层：

```text
弧操作 = select_arc(arcId, slots)   // 从池内 entry 条件满足的弧中选一条实例化
       | advance_arc(arcId)         // 当前阶段任务全部 commit 后推进
       | abort_arc(arcId)           // 中止当前弧
```

select 只能选 `entry.requires`（§7 语言）评估为真的弧；advance 校验该阶段展开任务已全部 commit；slots 绑定的实体必须存在且类型匹配。非法提议回执说明原因，Director 换提议。**边界（P4）：Director 在池内组合，不能写新弧、不能改弧的骨架**——它决定「世界接下来讲哪条主线、由谁在哪讲」，不发明主线本身；新弧只能来自内容管线（§14-7）。

### L2：Actor LLM（关键少数）

只给有名有姓、贯穿剧情的 NPC。从自己的菜单选择动作 + 参数，结构化 intent 提交。超时或失败自动降回 L0 兜底——**「L2 是 L0 的增强，不是替代」是内容校验硬规则（G21）**：声明为 L2 的 NPC 必须带完整 L0 profile（驱力、效用函数、行为树、画像），缺任一项内容草案不通过（§14-7）；没有 L0 兜底的 L2 在结构上不存在。运行时并发上限（如同时最多 3 个 L2 会话）；Director 可临时把某个 L0 NPC 升格为 L2（玩家突然和酒保深聊时），会话成本受统一预算控制。

三层合起来即降级阶梯的 NPC 部分：L2 是 L0 的增强，L1 是两者共用的指挥面。

## 4. 行动系统

### 4.1 intent 管线

```text
intent = { actor, verb, targets[], params, provenance }
         provenance: player | actor-L2 | director | stage-direction | menu-enrichment

菜单生成 → 选择 → 校验（资源/距离/状态/冷却/legality）→ initiative 排序
→ 逐个确定性结算（触发器级联、种子 RNG）→ 原子提交（timeline 事务）
```

非法 intent 带回执打回（有限重试），回执包含「提交值 vs 规则要求」的具体差异——复用 dsh-tavern MVU 的失败回执重试模式（`tests/mvu-tool-retry.test.mjs` 的行为形态）。

### 4.2 行动菜单：基础层 + 增富层

- **基础层**：引擎按当前状态计算全部合法动作（战斗态/对话态/探索态/商业态各自的动作表）。这是行动空间的边界本身。
- **增富层**：前台体验 Agent 提议的戏剧性选项（更贴合当前剧情的措辞与参数化变体），经 schema、白名单、去重校验后混入，并标注来源。**增富选项必须是基础层动作的参数化变体或场景可供性动作**——LLM 不能发明菜单外的新动作，只能让菜单更好看。此校验闭环直接移植 dsh-tavern 候选项生成的模式（`tavern-plugin/lib/domain/candidate-generation.js`：工具协议提交、类型白名单、去重、不足即拒绝）。

玩家看到的菜单 = 两层合并；拔掉 LLM，菜单自动只剩基础层。

**对话模式的两层（原待决「对话粒度」收敛于此，G22）**：对话态的基础层是**话题树**——内容期作者内容（话题节点、进入条件、效果载荷、分支），是对话的行动空间边界；增富层对当前话题做参数化变体与动态措辞，走上述同一校验闭环（只能是话题节点的参数化变体）。拔掉 LLM：话题树完整可玩，**离线对话不是空壳**；损失的只是戏剧性变体与动态措辞。

### 4.3 场景可供性（affordances）：环境动作的即兴入口

场景携带标签（沙地、悬崖、货架、酒馆桌、油渍、炼金台、铁匠铺……），标签解锁对应环境动作（扬沙、推落、躲入、点燃、按配方制作）。「我用沙子迷他的眼」这类即兴动作的合法形态是：**引擎依据场景标签生成环境动作，LLM/玩家只能提议或选择**，数值与成功率由引擎按标签规则确定。LLM 也不能凭空给没有标签的场景加动作。

### 4.4 条件可见性：一切门控的统一形态

等级限制、声望权益、商人库存门控、拍卖入场、雇佣分档、purse 不足、剧情分支解锁——全部收编为**同一个机制**：菜单/库存/权益条目携带条件表达式（§7），由菜单生成器在计算行动空间时逐条评估。这是 P3 的直接推论：行动空间封闭，意味着一切「解锁/限制」最终都表现为菜单条目的可见性条件。

```text
条目三态：可见（可执行）│ 锁定（显示 + 达成条件提示）│ 隐藏（不存在）
```

锁定还是隐藏是内容决策：声望权益倾向「锁定」以引导玩家努力达成；剧透性、剧情条件性内容倾向「隐藏」以保护体验。三态与达成条件提示由引擎渲染，与 LLM 无关。

触发器（状态侧）与条件门控（行动空间侧）**共享同一门条件表达式语言**（§7）：同一个 `faction_rep(x) >= 30`，在触发器里驱动事件，在门控里驱动菜单条目可见性——两侧行为不会漂移。

### 4.5 商业态交互模式

买入/卖出/以物易物/拍卖是与战斗态、对话态、探索态并列的**交互模式**，有专属动作菜单与结算形态：

- **双向账本转移是原子事务**：`player: 物品 -X, 金钱 +N` 与 `merchant: 物品 +X, 金钱 -N` 在同一 timeline 事务内提交；任何一侧校验失败（背包满、purse 不足、条件不满足）整笔回滚，不存在「钱付了货没到」的中间态。
- **以物易物**：双方物品各过定价引擎（§8.1）估值，差价金钱补齐。
- **拍卖**：出价/抬价/观望/离场菜单，引擎结算；成交价上限由定价引擎给出。L2 商人可在引擎给出的谈判区间内决策跟价或放弃。
- **谈判边界**：L2 商人的报价区间 `[定价×0.8, 定价×1.2]`（画像可调）由定价引擎给出；超区间提交被校验管线拒绝并带回执。L0 商人按价目表 + 画像修正，无谈判。

## 5. 实体系统：物品、装备、材料与自定义实体

### 5.1 实体结构：实例身份、能力槽与 loreRef

实体有两种身份，由来源决定：

- **模板堆叠**：普通材料与杂物按 `template + qty` 堆叠，无独立 uid。200 件杂物 = 少数堆叠条目，是账本性能与批量交易（§8.4）的基础。
- **唯一实例**：具名掉落（掉落表 `named` 标记）、遗迹遗物（物品池标记）、自定义成品（合成产出）带 `uid`，不堆叠，`provenance` 记录来源与血统链。

装备/技能类实体用**能力槽**表达特殊能力——`passive`（装备/携带即生效）、`active`（主动使用，带冷却）、`cost`（代价原语，诅咒式权衡）。槽内引用原语目录的效果原语 + 等级；遗迹物品的「特殊」体现在更高 rank、独占原语（仅特定物品池出现）与代价原语，全部由引擎定价定强度。

实体可携带 **loreRef**（世界观引用），与 lore 条目双向联动：描述投影按引用拉取背景（§5.4）；触发器按 `player_owns(loreRef: …)` 激活事件（§7）。一致性由内容校验器保证（§5.4、§14）。

示例（遗迹护符，唯一实例）：

```json
{ "uid": "item.inst.000318", "template": "relic.sun_amulet",
  "rarity": "epic", "basePrice": 900,
  "loreRef": "lore.sun_cult",
  "abilities": [
    { "slot": "passive", "primitive": "light_resist", "rank": 2 },
    { "slot": "active",  "primitive": "holy_burst",   "rank": 1, "cooldown": 3 },
    { "slot": "cost",    "primitive": "dark_penalty", "rank": 1 } ],
  "provenance": { "source": "location.sunken_temple", "turn": 47, "discoveryRoll": "seed:c7d2" } }
```

自定义成品沿用四层结构：**展示层**（名字/描述/风味，玩家或 ContentGen 提供，纯数据走消毒管道）、**机制层**（原语组合：效果原语 + 交付原语 + 兼容性约束）、**数值层**（引擎按点数预算定价，LLM 无权改数）、**经济与出处**（数量、售价、legality 标签、creator、配方、血统链）。自定义实体是一等公民：可交易、可库存、可被触发器引用、可被 Actor 使用。

### 5.2 「不被鼓励的玩法」的三个控制旋钮

1. **原语目录的收录范围**：不在目录中的效果，结构上不可能被组合出来。
2. **预算/成本曲线**：目录中存在但点数代价过高，可能但不经济。
3. **世界反应层**：legality 标签触发卫兵盘查、声望下降、物价波动——用设计出的游戏内后果表达不鼓励，而不是用系统禁止表达。

运行时不新增原语；原语目录只能随内容版本更新（版本化，见第 14 节），保证存档可迁移、平衡可审计。

### 5.3 材料、配方与特质继承

即兴系统的材料侧。**材料携带 essence 标签，从来源继承**：boss 的特质（毒亲和、庞躯）继承到掉落材料；遗迹的主题标签（光、暗）继承到遗物。**配方是「essence → 效果原语」的映射表**（规则库数据）：

```json
{ "recipe": "craft.medicine.bone_broth",
  "station": "alchemy_table",
  "materials": [ { "tag": "bone", "qty": 1 } ],
  "essenceMapping": {
    "poison_affinity": { "primitive": "poison_resist", "rankFrom": "material" },
    "colossal":       { "primitive": "max_hp_up", "rank": 1 } } }
```

**特质一致性由构造保证**：标签沿「来源 → 材料 → 成品」继承，路径上没有 LLM 插手的位置。同一根 boss 骨头，制药走 `poison_affinity → poison_resist`，制武器走同一标签 `→ poison_on_hit`——药给抗毒、武器给淬毒，都从同一标签出发，一致性天然成立。

**血统链（lineage）**：成品 provenance 记录完整链（`boss → 材料uid → 成品`），供触发器条件（§7 的 lineage 谓词）与叙事检索引用——「这把武器出自蚀骨巨蟒」是可查询的事实。

### 5.4 描述投影：事实到文案的渲染层

P2 的镜像原则：**描述从结构化事实渲染，事实永不从描述抽取**。

```text
描述投影 = [基础] 模板文案
           [来源] provenance 事实行（来源、回合、具名标记）
           [背景] loreRef 检索到的背景摘要（可选）
           [风味] Narrator/ContentGen 按上述事实润色的缓存（可选）
```

- 风味缓存是**数据**：版本化、可重渲染、可丢弃。拔掉 LLM 降级为前三行，信息零丢失；来源说明不可能说谎——它渲染自 provenance 字段，而 provenance 由引擎写入。
- **内容校验器**：ContentGen 产出的物品草案入库前过一致性校验——效果原语与 loreRef 指向条目的主题标签关联性（神殿带 `light` 标签 → 光系原语）、命名规范（长度/字符集）。不通过则告警，人工裁决。

## 6. 玩家文本边界与注入防御

- 行动层零自由文本（P3）。玩家唯一的文本输入是**命名与风味**：角色名、物品名、风味描述、留言。长度与字符集受限。
- 这些字符串永远是**数据不是指令**。它们会流入 LLM 上下文（比如叙事 Agent 要描写「蝰蛇之吻」），因此必须有统一消毒管道：长度/字符集校验 → 定界符包裹并标记为不可信数据 → 进入提示词 → 注入审计。恶意命名（如把物品名写成指令注入）不得影响任何 Agent 行为。
- 行动合法性、数值、状态变更与玩家文本完全正交。

## 7. 条件表达式语言

触发器条件、任务阶段要求、菜单/库存/权益门控（§4.4）、弧入口与分支（§10）四处需求同构，共用**一门小的、确定性的、可序列化的表达式语言**——收编为一门语言的目的正是 G14 的收敛：避免多套门控逻辑各自演化、行为漂移。

```text
player_level >= 8                                  // 角色谓词
faction_rep(grey_wolves) >= 30                     // 势力谓词
npc_affinity(elder_yun) > 20                       // 好感谓词
player_owns(tag: "bone_of_bone_maw")               // 物品谓词（tag/template/uid）
player_owns(loreRef: "lore.sun_cult")              // 物品谓词（世界观引用）
lineage_of(weapon.inst.000412) includes "boss.bone_maw"   // 血统链谓词
item_delivered(npc: "elder_yun", tag: "…")         // 事件谓词
market_index(category: "metal", region: "mountain") < 1.2 // 经济谓词
region_controlled_by("capital") == "lords"         // 区域控制谓词（G15）
region_contested("border_march")                   // 交战状态谓词（G15）
quest_stage(main_quest) == 3                       // 任务谓词
arc_stage(arc.rebellion) == "uprising"             // 弧阶段谓词
scene_tag("alchemy_table")                         // 场景谓词
… 支持 and / or / not 组合
```

三条硬规则：

1. **评估是纯函数**：输入 = 权威状态快照 + 规则版本，输出 = 布尔。无副作用、无 LLM、同输入同输出（P7）。
2. **语言随规则库版本化**：表达式是数据，存档记录其版本；谓词集合只能随内容版本扩展，不删旧语义。
3. **谓词只读权威状态**：查询物品走账本索引，查询事件走事件日志，不扫描叙事归档。

## 8. 经济子系统

经济是纯引擎子系统（LLM 零参与）——五 case 中「大量杂物出售」全程无 LLM，正是 P1 的正面压力测试。

### 8.1 定价引擎

定价函数注册表，规则库一等组件。**定价是纯函数**，输入全为结构化字段：

```text
price = f(base, rarity系数, essence溢价, 市场因子(§8.3), 商人画像修正)
买入价 = price × 画像溢价系数    卖出价 = price × 画像折价系数
谈判区间 = [price × 0.8, price × 1.2]（画像可调），超区间提交被校验拒绝
```

商人画像（贪婪度、对各类 essence/类别的偏好）是 NPC 数据字段。定价函数版本化，平衡性统计测试（§14）直接跑它。

### 8.2 商人库存与 purse

- **库存表**：条目携带 `region` 标签与条件表达式（等级/声望，走 §7 语言与 §4.4 三态门控）、刷新周期与进货额度。**进货表解析链：店铺所在地区 → 该区域当前控制势力（§11 区域控制账本）→ 对应势力的进货表**——叛军占领的山城进叛军货。地域特征从静态地理升级为「地理 × 控制势力」（G15 传导）。
- **purse（拟态模型）**：NPC 钱包是「有上限、按周期恢复」的状态字段，不是真实货币循环。收购扣减 purse，purse 不足时收购条目锁定并提示原因。拟态起步；「状态化」（金钱真实流转）为进阶选项，升级条件见 §16。
- 收走的货物进商人库存，可被其他 NPC/玩家买走；刷新周期后按销货率清除。

### 8.3 市场状态账本

世界经济的确定性实现：**按「物品类别 × 区域」的供需指数做成账本条目**。所有买卖都更新它（买入 = 需求 +，卖出 = 供给 +），定价引擎读它作市场因子。

- **涌现行为**：玩家倾销 80 把破剑 → 金属类供给 +80 → 山地区域金属指数下移 → 后续收购价下降。倾销压价是确定性涌现，不是脚本。
- **漂移**：世界事件经触发器驱动（战争爆发 → 铁价 ×1.5）；指数按周期向基线回归。
- **控制态传导（G15）**：contested 区域市场因子加成波动（围城 → 补给短缺 → 物价上浮）；区域控制变更（§11）本身是漂移事件（新势力税制 → 类别价格曲线变化）。
- **防通胀阀门**：市场因子本身就是阀门——刷卖收益边际递减，无需封顶数字。

### 8.4 批量交易

杂物按模板堆叠（§5.1），200 件 = 少数堆叠条目 × qty。批量卖出 = **单事务批量 ledger delta**（多行 remove + 一行 gold add）+ 汇总式审计记录（itemLog 尾日志模式扩展为可配置长度/汇总式）。账本分级记录：rarity 分档定价（白 1×、绿 2×、蓝 4×…）。

## 9. 声望、好感与阵营归属

- **两级模型**：势力声望（per-faction 账本条目）与个体好感（per-NPC 条目）分离又联动——同势力 NPC 的基础好感 = f(势力声望)，个体互动（对话、赠礼、任务）独立修正。数值全部由引擎经 intent 维护。
- **membership（阵营归属）是可变更的权威字段（G16）**：触发器、结算效果与弧阶段 hook（§10）都可变更 NPC 的 membership，变更写审计（何时、由何事件/弧阶段）。倒戈的传导：两级好感的基础项随 membership 重算——对旧势力的基础好感解除，对新势力的基础好感 = f(新势力声望)；**个体修正保留**（倒戈队长对玩家的私人恩怨不变）。忠诚驱力重定向（L0 效用函数，§3）；权益门控（§4.4）按 membership 解析 `faction_rep` 引用——他的商店折扣跟随新势力。
- **硬约束与审计**：声望/好感变更都是原子 delta，上下限 [-100, 100]，来源审计（quest id / 互动事件 id / membership 重算事件）写入账本。
- **权益 = 条件门控**（§4.4 + §7）：拍卖入场（`faction_rep >= 30`）、雇佣兵分档（30 可雇普通兵、60 可雇精锐）、商店折扣、剧情分支。声望为负走同一语言的反面：触发敌对（卫兵攻击、该势力商店物价上浮——联动 §8.3 市场因子）。
- **里程碑演出（数值与演出分离）**：Director 在声望跨阈值时安排演出拍（团长接见、`act_respect` 舞台指令）；L2 NPC 的 POV 注入声望事实，对话态度随之变化；L0 NPC 的好感数值直接进效用函数（态度参数）。拔掉 LLM：声望数字、权益解锁、物价反应、membership 传导照常，只有演出消失。

## 10. 故事弧（arc）：主线故事池

任务图（quest graph）管单条委托的静态阶段；「一条主线」——贯穿几十回合、可依世界状态选择走向的宏观剧情——需要专门的数据落点。**故事弧（arc）是内容期产出的宏观剧情资产**，全部存放于故事池（arc pool）；运行时只实例化、推进与中止，**不创作**（G17）。

```json
{
  "arcId": "arc.rebellion",
  "entry": { "requires": "faction_rep(lords) < -20 and region_controlled_by('capital') == 'lords'" },
  "activation": "director",
  "slots": [ "rebel_leader:npc", "capital:region", "rebels:faction" ],
  "stages": [
    { "id": "spark",    "summary": "民怨积累，密谋初起",
      "branchOn": [ { "next": "uprising", "when": "player_owns(tag: 'rebel_charter')" },
                    { "next": "suppressed", "when": "not player_owns(tag: 'rebel_charter')" } ] },
    { "id": "uprising", "summary": "叛乱爆发，首府围城",
      "hooks": [ { "effect": "region_control.set_contested", "args": { "region": "$capital" } } ] },
    { "id": "aftermath", "branchOn": [
        { "next": "crown_change",  "when": "region_controlled_by($capital) == $rebels" },
        { "next": "suppression",   "when": "not region_controlled_by($capital) == $rebels" } ] }
  ]
}
```

五条设计规则：

1. **弧是骨架不是剧本**：stages 定关键事件与走向（指导，不照演——对应 dsh-tavern 剧本游标的「剧本走向」语义）；`slots` 是参数槽，实例化时绑定具体实体（哪个 NPC 当叛军领袖、哪座城当首府）——同一弧在不同世界状态实例化出不同剧情。
2. **入口条件与分支走 §7 语言**：哪些弧「可被选中」、下一阶段走哪条分支，都是世界状态的纯函数。**激活模式由弧资产声明**：`auto`——入口满足即确定性实例化，无需 Director（P5 对主线同样成立）；`director`——进入可选池，由 Director 的弧操作通道（§3 L1）择一实例化（关键主线交给导演编排，也避免条件满足即自动开播挤占并发弧预算）。
3. **弧阶段与任务图对齐**：每个 arc stage 展开为一组任务（quest graph）；任务阶段机继续管单任务的 prepare→commit（两阶段提交）；**弧阶段在其展开任务全部 commit 后才前进**，`branchOn` 在阶段 commit 时评估——两阶段思想从任务级抬到弧级。
4. **效果钩子也是 intent 模板**：`hooks` 只引用引擎的效果原语（如 `region_control.set_contested`），阶段 commit 时按模板生成 intent 走同一校验管线——不是自由脚本。
5. **池内不发明**（P4）：运行期只能选弧、推进弧、中止弧（Director 的弧操作通道见 §3 L1）；新弧只能来自内容管线（§14-7），版本化随规则库。

存储：弧资产在规则库（版本化）；实例化状态（当前弧、阶段、槽绑定、分支历史）在权威状态，走 timeline 事务。并发弧数量与粒度预算见 §16 待决。

## 11. 数据存储

需求：引擎和 LLM 都能自动读取与修改，且高效。答案是**单一权威存储 + 两个门面**：

```text
                    ┌─ 引擎门面：类型化 API，事务内同步读写
权威状态存储 ────────┤
（timeline 事务）    └─ LLM 门面：只读工具（投影/检索/查询）+ 只写工具（intent 提交）
                              两条路汇入同一条 timeline，审计日志记录作者
```

| 层 | 内容 | 写入者 | 存储方式 |
|---|---|---|---|
| 权威游戏状态 | 世界/遭遇/角色/变量，分片（world / encounter / actors / ledgers） | 只能是引擎（经事务） | 事件溯源 + 内容寻址增量块，重放校验 |
| 账本 | 物品/NPC/任务/地图/**市场状态**/**声望好感**/**区域控制**（region → controller + contested，G15）/membership，类型化硬约束 | 引擎（LLM 经 intent） | 与状态同事务，带审计尾日志；支持批量 delta 与实例身份（§5.1、§8.4） |
| 规则库 | 原语目录、公式、**定价函数**、遭遇表、**配方**、**商人库存表**、触发器、**条件表达式**、**故事弧池**、**话题树**、**模板文案库**（intent 索引）、舞台指令词汇表 | 开发者/ContentGen（校验后） | 规则即数据 + 版本号，存档记录规则版本 |
| 自定义实体库 | 玩家/ContentGen 组合的实体 | 引擎（组合校验+定价后） | 一等游戏对象 |
| 叙事归档 | 每回合正文 + 事件流 | 追加 only | 分轮存储 + 检索索引 |
| 上下文投影 | 各 Agent 的 POV 视图 | 引擎派生，可缓存 | 不落权威盘；稳定前缀分层缓存 |

效率要点（均移植自 dsh-tavern）：增量内容寻址存储让几百回合存档不膨胀（`tavern-plugin/lib/domain/incremental-json-state.js`）；长战役靠自动压缩治理（`tavern-plugin/lib/domain/auto-compaction.js`）；「LLM 自动读取」= 每回合 Context Planner 自动为每个 Agent 准备投影（稳定段缓存命中 + 动态段本回合新增，`tavern-plugin/lib/domain/context-planner.js`）；「LLM 自动修改」= intent 工具提交后经校验原子应用。

## 12. 运行框架

### 12.1 回合制管线（严格顺序）

```text
[回合 N]
 0. 开局触发器     回合开始效果 tick，开场事件，到期延迟事件执行（见级联预算）
 1. 感知构建       为每个决策者生成 POV 投影（Context Planner 预算内）
 2. 菜单生成       基础层（引擎，含 §4.4 条件门控三态评估）
                  + 增富层（前台体验 Agent，校验后混入）
 3. 决策收集       玩家选菜单（同步）│ L2 NPC：Actor Agent（并行，带 deadline）
                  │ L0 NPC：效用 AI（毫秒）│ 舞台指令已注入为偏置
 4. 校验排序       合法性校验（非法带回执重试或拒绝）+ initiative 排序
 5. 结算           逐 intent 确定性结算，触发器级联（深度上限），种子 RNG 记录；
                  商业态结算为原子双向账本转移（§4.5）；大事件级联受独立预算
                  约束并触发延迟结算（见下）
 6. 提交           原子事务：timeline.apply → revision++ → 账本 → 归档 → checkpoint；
                  任何一步失败，整回合回滚（prepare/stage/finalize/discard 四段式）
 7. 叙事渲染       事件流 → 正文（并为 L0 NPC 代笔台词）；仅入归档
 8. 导演审查(每N)  发舞台指令 + 任务阶段提议（图内）/ 弧操作提议（池内）（走校验）
[回合 N+1]
```

- 唯一的并行点是步骤 3；延迟大头是 3（LLM 决策）与 7（叙事渲染）。回合制玩家可接受 5–10 秒，正好覆盖「并行决策 + 一次渲染」。步骤 5 纯代码，毫秒级。
- 步骤 6 的原子性照抄 dsh-tavern 的回合生命周期（`tavern-plugin/lib/domain/turn-orchestration.js` 的 prepare/stageChanges/finalize/discard）：半提交状态在结构上不存在。
- **大事件级联预算与延迟结算（G19）**：改朝换代、战争爆发是跨势力、跨区域的级联，单回合深度预算既可能不够，也会让世界剧变在同一回合瞬间完成（体验差）。级联拆分为「立即效果」（本回合提交：首府易主、contested 置位）与「传导效果」（排入延迟事件队列，按到期回合扩散：进货表下回合刷新、市场因子漂移再下回合、声望/好感/membership 重算随后），由后续回合的步骤 0 执行。事件日志记录每次传导的到期回合——重放确定（P7），世界剧变有过程感。

### 12.2 即时制变体

同一套内核，只改调度策略：

```text
tick 循环（如 10Hz 确定性模拟）
  ├─ LLM 顾问请求带 TTL（如 2s）
  ├─ intent 只在 tick 边界落地，且过 revision 门控：
  │    世界已从「该决策所依据的 revision」前进 → 判 stale，丢弃或重新决策
  └─ 叙事完全异步流式
```

即：**回合制 = 所有决策都等齐的 tick；即时制 = 决策只是建议的 tick**。revision 门控机制（dsh-tavern 用它拒绝迟到的后台任务结果，`story-timeline.js` 的 basedOn 校验）在即时制里天然充当「AI 反应过时」的过滤器。延迟结算队列在即时制中按 tick 到期执行。

### 12.3 降级阶梯（P5 的运行时形态）

```text
LLM 正常 → 全体验验
LLM 超时 → 对应 NPC 落回 L0；菜单剩基础层（对话态 = 话题树）；文案按 intent 从模板文案库渲染（§3、§14-7）
LLM 宕机 → 同上，游戏完整可玩（引擎、菜单、结算、存档均不依赖 LLM）；
           director 模式弧不实例化/不推进，auto 模式弧按入口条件确定性推进，
           确定性任务与事件照常
```

## 14. dsh-tavern 没有、必须新增的硬需求

1. **种子 RNG + 确定性重放**：事件日志记录每次掷骰的种子与结果；同输入必须同输出。延迟结算事件的到期回合同样入日志（§12.1）。
2. **规则版本化与存档迁移**：原语目录、公式、定价函数、遭遇表、配方、库存表、条件表达式、**故事弧池**都有版本号；旧存档遇到新规则有确定性迁移路径。
3. **平衡性统计测试**：无头 API 跑几千局全模拟（L0 NPC 无 LLM，正好全自动），出数值分布与胜率曲线；定价函数、掉落表与弧分支覆盖是重点对象。
4. **LLM 延迟 SLO 与降级策略表**：每类调用（决策/渲染/增富/导演）各自的 deadline、超时行为、降级路径，落成配置而非散落代码。
5. **Prompt 注入防御**：玩家命名数据流经 LLM 上下文（第 6 节），消毒管道与注入审计是硬需求，不是可选加固。
6. **L2 会话成本模型**：并发上限、升降级策略、按需唤醒与回收（参考 dsh-tavern 后台会话 5 分钟空闲回收的实践）。
7. **内容管线与校验器**：掉落表、物品池、配方、库存表、任务图、lore、**故事弧池**、**话题树**、**模板文案库**均为内容期产物。模板文案库按 intent verb 索引、带画像/语气参数，是 L0 台词与一切降级文案的唯一来源（§3、§12.3）。校验硬规则：① 效果原语与 loreRef 主题标签关联、弧骨架结构/槽类型/效果钩子合法性、命名规范；② **声明为 L2 的 NPC 必须带完整 L0 profile**（驱力、效用函数、行为树、画像），缺任一项不通过；③ 模板文案库覆盖全部基础 intent verb，缺 verb 即告警。ContentGen 草案过校验后人工审校入库；运行时只消费不生产。

## 15. 里程碑

- **M0 内核切片（纯代码，零 LLM）**：timeline 事务 + 回合管线 + 账本（含实例身份与批量 delta）+ L0 效用 AI + 菜单基础层与条件门控三态 + 定价引擎与 purse 最小闭环 + 无头 API。验收：两阵营互殴 10 回合；可存档、可重放、可分支；门控三态与批量交易行为测试；无头跑 1000 局出数值分布。
- **M1 第一批外设**：前台体验 Agent（正文渲染 + 菜单增富，双任务模式）。验收：拔掉 LLM 仍完整可玩（模板文案库与话题树在位：NPC 不哑巴、对话非空壳，G20/G22）；增富选项 100% 合法（校验闭环测试）。
- **M2 Director + 舞台指令总线（L1）+ 弧操作通道 + 任务阶段机**。验收：指令可审计；物理能力校验拒绝非法指令且回执正确；弧提议校验（select 仅限 entry 满足的弧、advance 仅限任务全 commit）；弧阶段两阶段推进。
- **M3 Actor L2 + 自定义实体 + 市场状态账本 + 区域控制账本 + membership + 即时制变体**。验收：L2 超时自动降级；自定义毒药全流程（材料特质继承 → 组合 → 定价 → 交易 → 使用 → 触发器引用）；倾销压价的确定性涌现（重放同结果）；membership 变更与好感重算；**改朝换代全流程（弧实例化 → 叛乱胜利 → 首府易主 → 进货表/市场/声望传导 → 延迟结算）重放同结果**。
- **M4 ContentGen + 长战役**：压缩、检索、离线资产生产管线与内容校验器（含故事弧草案校验、L2 必有完整 L0 profile 的硬规则、模板文案 verb 覆盖检查）。
