# RPG 引擎模块拆分与开发顺序

> 状态：模块拆分稿 v1.0（2026-10-09）。配合设计稿 v0.5（§x 指该稿）、技术选型稿 v1.0（`rpg-engine-tech-stack.md`）使用。回答：技术栈与整体框架已定，如何拆分开发模块、以什么顺序做、每个模块细化设计时写什么。架构总图见 `rpg-engine-architecture.html`。

## 0. 拆分原则

| # | 原则 | 含义 |
|---|---|---|
| D1 | 依赖单向 | 模块只能依赖更低层的模块；kernel 内零外部依赖（技术选型稿 §4 硬规则）。一个模块 = 一个可单独重构/替换的边界 |
| D2 | 可独立验收 | 每个模块带自己的行为测试；被依赖的下层模块用接口 + fake，不要求先行完成 |
| D3 | 数据契约先行 | intent / 事件 / 状态 schema 是所有模块的公共语言（P2/P7 的载体），最先落地 |
| D4 | 模块边界对齐设计稿章节 | 模块清单 ↔ 设计稿 §3–§12 一一对应，验证 case 集（G1–G22）可逐模块映射回归 |
| D5 | 粒度 | 单模块 ≈ 1–2 周量级：过大按数据/行为再拆，过小并入宿主模块 |

协议次序（对「先定制协议」的落地）：**现在定骨架，M0 后冻结**——`contract`（M01）+ 协议信封（M15 的 schema 部分）先行，因为它们是公共语言；`protoVer` 冻结放在 M0 跑完、M1（Web 台 / Godot G1）动工前。理由：协议细节（菜单三态的事件表达、批量结算的事件粒度）会被 M0 实证修订，冻结太早 = 把返工焊死。

## 1. 模块分层与依赖图

```text
L5 宿主      cli        server+web   llm        sim        content(校验器)
              └────────────┬──────────┘          │           │
L4 seam                api ── protocol           │           │
                        └────────────┬───────────┴───────────┘
L3 编排              turn ── quest
                     └──┬─────────┬─────────┬─────────┬─────┘
L2 行为        menu    ai      economy    settle
              └──┬─────┴─────────┬──────────┴───┬─────┘
L1 状态     ledger   entity    rules    trigger
            └──┬──────┴─────────┬─────────┬─────┘
L0 基石       timeline    expr    rng
              └───────────┴───────┴─────┘
                      contract（公共数据契约，被全部依赖）
```

> `contract` 是类型与 schema 包（无行为）；`storage`（fs 端口实现）与 `llm` 一样属于外层，接口定义在 kernel 被依赖处。

## 2. 模块清单（20 个）

### L0 契约与基石

| # | 模块 | 职责 | 对应设计稿 | 依赖 | 独立验收 |
|---|---|---|---|---|---|
| M01 | `contract/` | 公共数据契约：GameEvent 判别联合、权威状态分片（world / encounter / actors / ledgers）、intent schema、revision/seq 语义、菜单三态形态 | §4.1 / §11 | 无 | Zod schema + TS 类型导出 + 往返序列化测试 |
| M02 | `rng/` | PCG32：world/combat/loot 分流、状态可序列化、掷骰事件入日志 | §14-1 | contract | 同种子同序列；参考向量测试 |
| M03 | `expr/` | 条件表达式语言：词法 → 递归下降解析 → 版本化 AST → 纯函数求值；谓词注册表（只读权威状态快照） | §7 | contract | 全部谓词样例；求值无副作用；坏表达式报错定位 |
| M04 | `timeline/` | 权威状态机：apply / revision++ / branch / checkpoint / basedOn stale 拒绝；`fold(events) ≡ snapshot` | §13（story-timeline 移植） | contract | 重放等价 golden 测试；分支后重放一致 |

### L1 状态机制

| # | 模块 | 职责 | 对应设计稿 | 依赖 | 独立验收 |
|---|---|---|---|---|---|
| M05 | `ledger/` | 账本：物品（堆叠/实例身份）、金钱、声望好感、membership；原子 delta、硬约束（[-100,100] 等）、审计尾日志、批量 delta | §5.1 / §8.4 / §9 / §11 | timeline, contract | 双向转移原子性（任一侧失败整笔回滚）；批量 200 件 = 少数条目 |
| M06 | `entity/` | 实体系统：模板/uid 生成（计数器派生）、能力槽、essence 继承、血统链、自定义实体组合校验 | §5 | contract | 具名掉落升级唯一实例；特质一致性由构造保证 |
| M07 | `rules/` | 规则注册表：原语目录（效果原语 = 纯函数注册）、定价/配方/掉落/遭遇表/库存表加载、版本号 + 迁移注册表 | §5.2 / §8.1 / §14-2 | contract, entity | 内容文件加载校验；旧版本规则 → 迁移路径测试 |
| M08 | `trigger/` | 触发器引擎：条件（expr）→ 效果原语；级联深度预算；延迟结算队列（到期回合执行） | §12.1 / §13 | contract, expr, timeline | 级联深度上限生效；延迟事件到期执行且重放确定 |

### L2 行为

| # | 模块 | 职责 | 对应设计稿 | 依赖 | 独立验收 |
|---|---|---|---|---|---|
| M09 | `menu/` | 行动菜单基础层：战斗/对话/探索/商业态动作表、三态门控（expr 逐条评估）、场景可供性标签、话题树挂载 | §4.2 / §4.3 / §4.4 | contract, expr, rules, ledger | 三态与 hint 渲染；菜单外动作结构上不存在（P3） |
| M10 | `ai/` | L0 NPC：驱力 + 效用函数 + 行为树；舞台指令偏置注入（L1 解释器）；种子扰动 | §3 | contract, menu, ledger | 百人混战毫秒级；同种子同决策；指令偏置生效 |
| M11 | `economy/` | 经济：定价纯函数（base×rarity×essence×市场×画像）、purse 拟态、市场状态账本（供需指数/漂移/回归）、谈判区间 | §8 | contract, rules, ledger | 倾销压价涌现，重放同结果；超区间提交被拒 |
| M12 | `settle/` | intent 校验与结算器：合法性校验（资源/距离/状态/冷却/legality）→ initiative 排序 → 逐 intent 结算（调效果原语 + rng）→ 失败回执（提交值 vs 规则要求）；商业态原子双向转移 | §4.1 / §4.5 | contract, rules, ledger, entity, rng, trigger | 非法 intent 带差异回执；回执重试闭环；级联预算受控 |

## 3. 开发批次（4 批到 M0，第 5 批进 M1）

| 批次 | 模块 | 产出 | 收口验收 |
|---|---|---|---|
| **B0 契约与基石** | M01 → M02 / M03 / M04（并行） | 可重放的「空转引擎」：状态分片 + 事件日志 + 分支，无回合逻辑 | `fold(log) ≡ snapshot`；同种子双跑日志逐字节相等；分支重放一致 |
| **B1 状态机制** | M05 / M06 / M07（并行）→ M08 | 账本/实体/规则可独立操作，触发器可级联 | Case 1 的 T0 部分（掉落入库、实例升级）可单测跑通 |
| **B2 行为** | M09 / M10 / M11 / M12（并行，接口先行） | 一回合的完整机制：菜单 → 决策 → 结算 | Case 1 的 T2/T3（定价、特质继承）、批量交易原子性 |
| **B3 编排 + seam** | M13 → M16 → M15 / M17 / M19 | **M0 全验收**：两阵营互殴 10 回合、可存档/重放/分支、门控三态、批量交易、千局分布 | 设计稿 §15 M0 验收清单逐项过 |
| **B4 外设（M1）** | M18 → M20，M15 冻结 protoVer | 前台体验 Agent（Mock → 真模型）+ Web 调试台 | 拔 LLM 完整可玩；增富选项 100% 合法 |

并行开发的约定：**每批开工前先冻结该批的模块接口**（在 `contract/` 或各模块 `port.ts` 里定义），批内模块互不依赖实现、只依赖接口——这是 D2 的落地方式。`settle`（M12）是 B2 的汇聚点，接口最重，先定。

## 4. 单模块设计稿模板

每个模块一份 `docs/design/modules/Mxx-<name>.md`，固定结构（对齐 D4）：

```markdown
# Mxx <模块名>
> 对应设计稿：§… ；批次：B… ；依赖：M… ；被依赖：M…

## 1. 数据模型与不变量        # 类型定义 + 必须永真的约束（违反即 bug）
## 2. 公开接口                # 函数签名（纯函数优先，副作用走 timeline）
## 3. 依赖端口                # 引用的下层接口（及测试用 fake）
## 4. 事件产出                # 本模块产生哪些 GameEvent（进事件日志的形状）
## 5. 测试与验收              # 单测 + 行为测试；映射验证 case（G…）
## 6. 开放问题                # 留给实现期决策的点
```

两条模板硬规则：

1. **§4 事件产出必填**——事件形状是模块间唯一的真实耦合面；先写事件，再写代码（事件 = 契约的实例）。
2. **§1 不变量必写**——每条不变量至少对应一条测试断言（如「声望 ∈ [-100,100]」「半提交状态不存在」）。

## 5. 模块 ↔ 验证 case 回归映射（示例）

| Case | 主要模块 | 回归断言 |
|---|---|---|
| Case 1 Boss 掉落骨头 | M06/M07/M11/M12/M08 | 实例升级、特质一致、定价纯函数、触发交付 |
| Case 5（若有批量交易） | M05/M11/M12 | 批量 delta 原子性、purse 锁定 |
| Case 6 政权更迭 | M08/M14/M05 | 级联预算、延迟结算、membership 重算 |
| Case 7 拔 LLM | M13/M18/M07(templates) | 降级阶梯、模板文案、话题树可玩 |

M0 只需覆盖前两行；后两行在 M2/M3 收口时启用——验证 case 集本来就是回归基准，模块化后回归有了明确挂载点。

## 6. 风险与拆分修正预案

| 风险 | 预案 |
|---|---|
| `settle`（M12）过大（校验 + 排序 + 结算 + 回执四件事） | 先按「校验器 / 结算器」内部两文件起步；若实现期超 2 周，正式拆成 M12a/M12b |
| `contract` 膨胀成「什么都放」的垃圾场 | 只放跨模块共享的 schema；模块私有类型留在模块内导出 |
| B2 四模块并行时接口漂移 | 接口冻结（§3 约定）+ CI 里跑各模块的行为测试（依赖 fake 不依赖实现） |
| `turn` 成为上帝模块 | 只做编排（八步顺序与预算调度），任何判定/数值逻辑下沉到 L1/L2；turn 内禁止出现游戏规则 |
